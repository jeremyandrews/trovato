## Key implementation facts a successor must know (see also commit messages)
- `FileStorage::read_stream` has a DEFAULT impl (reads via `read()` then slices in memory via
  the new `memory_stream()` helper) so existing test-double `FileStorage` impls across the test
  suite did not need updating.
- `object_store`'s `ObjectStore::delete()` (what `S3FileStorage::delete` uses) goes through the
  S3 **Bulk Delete** API (`POST /{bucket}?delete`, XML body) by default, not a plain per-key
  DELETE. Discovered this because the fake S3 server's first version only implemented a plain
  DELETE route and silently "succeeded" (404 mapped to Ok) without deleting anything — see
  `crates/kernel/tests/common/fake_s3.rs`'s `bulk_delete` handler and doc comment.
- The in-process fake S3 server (`crates/kernel/tests/common/fake_s3.rs`, no Docker available
  in this sandbox) requires an `Authorization` header to answer anything but 403 on GET — not
  real SigV4 verification (nothing to check a signature against), just enough to keep
  `the_bucket_does_not_answer_an_unsigned_request` meaningful, since `object_store` always signs
  and a plain unauthenticated `reqwest::get` does not.
- `file_storage_conformance_test.rs` and `file_storage_s3_serving_test.rs`'s `s3_config()`
  helpers now fall back to `fake_s3::ensure(...)` when `TROVATO_TEST_S3_ENDPOINT`/`BUCKET` are
  unset, instead of skipping — CI always sets those (real MinIO), so CI behavior is unchanged;
  this only adds real local coverage. `file_record_import_s3_test.rs` (new file) and the new
  SERVE_UNMANAGED_FILES tests in `file_storage_s3_serving_test.rs` use the same pattern.
- Only ONE extra `TestApp` is created for the SERVE_UNMANAGED_FILES=false tests in
  `file_storage_s3_serving_test.rs` (not two) — an earlier version with two extra apps hit
  intermittent Postgres connection-pool timeouts in this resource-constrained sandbox when run
  as part of the full file (passed in isolation, failed as part of the full 15-test file); the
  default-`true` case was changed to reuse the existing shared S3 `fixture()` instead.
- `trovato_kernel::file::range::resolve_range` is reachable but NOT re-exported at the
  `file::` module top level (only `ByteRange`/`RangeNotSatisfiable`/`is_range_not_satisfiable`/
  `parse_range_header` are); `fake_s3.rs` calls it via the full path.
