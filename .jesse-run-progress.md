## Locked design decisions (read this before touching anything)

- **Media types = 4 content types**, declared by `trovato_media` via the existing
  `tap_item_info`/`ContentTypeDefinition`/`FieldDefinition` machinery (no new field system):
  `media_file` (field_file, File, required), `media_image` (field_file required + field_alt_text +
  field_caption + field_credit), `media_remote_video` (field_remote_url Text required + field_caption),
  `media_remote_embed` (field_embed_url Text required + field_caption). Title field = media's name.
- **Plugin seam**: new tap `tap_media_source() -> Vec<MediaSourceDefinition>` (plugin-sdk/src/types.rs),
  dispatched at boot in state.rs exactly like `tap_admin_nav` (in-memory `MediaSourceRegistry`,
  crates/kernel/src/plugin/media_source_registry.rs, modeled on admin_nav_registry.rs). trovato_media's
  own `tap_media_source` registers its 4 types; a later plugin adds more (e.g. document preview) the
  same way. Add "tap_media_source" to KNOWN_TAPS in plugin/info_parser.rs.
- **Permissions** (flat, exact Drupal names, NOT per-content-type): `access media overview`,
  `create media`, `edit own media`, `edit any media`, `delete own media`, `delete any media`.
  Declared by trovato_media's `tap_perm`. Enforced via trovato_media's `tap_item_access` (checks
  `input.user_permissions` directly against these flat names for item_type in the 4 media types) —
  this is the existing per-item access-tap extension point, NOT a new generic own/any-by-type
  mechanism (the kernel's generic `"{op} any/own {type}"` fallback would derive per-type names like
  "edit any media_file", which is NOT what the spec wants, so we bypass it with an explicit Grant).
  IMPORTANT: do NOT reuse kernel's generic `/admin/content/{type}/add` or `/admin/content/{id}/edit`
  routes for media — their permission gates are hardcoded ("create {type} content", "edit any content"
  pre-gate) and don't match the flat media permissions. Build dedicated routes instead (see below),
  reusing `item_form::{build,process,requested_publishing,redisplay,wants_preview}` (pub(crate),
  callable from a sibling routes module) and `state.items().check_access(item, op, user_ctx)` directly.
- **Usage tracking = generic, not media-specific at write time.** New kernel table `item_reference`
  (referencing_item_id, referenced_item_id, field_name, created) populated by a new
  `crates/kernel/src/content/media_refs.rs` (modeled closely on file_refs.rs), extracting every
  `FieldType::RecordReference(_)` field's value(s) (CategoryReference is a different enum variant,
  excluded automatically) on every item create/update. Call sites: item_service.rs right after the
  two `Item::create_with_file_refs`/`Item::update_with_file_refs` calls (~line 952 and ~1776), logging
  on error (non-fatal, not threaded through the file_refs transaction — acceptable per spec, usage
  tracking is UX not correctness-critical). "Media usage count" is then just
  `SELECT COUNT(*) FROM item_reference WHERE referenced_item_id = $1` at read time (library/delete
  routes), joined against the media source registry only there. No registry dependency at write time.
- **Picker widget**: `FieldType::RecordReference("media")` is the sentinel a content type uses to get
  the picker (literal target_type string "media" means "any registered media source type"; no support
  for restricting to one specific media type for now — not required by spec, kept simple). In
  `crates/kernel/src/content/form.rs`'s `widget()` match arm for `RecordReference`, special-case
  `target_type == "media"` to emit `FormElement::widget("media_reference")` instead of
  `"record_reference"`, following exactly the precedent of the existing `target_type == "category_term"`
  special-case right above it. New template `templates/form/widget--media_reference.html`, new JS
  `static/js/media-reference-picker.js` (native `<dialog>`, modeled on static/js/admin-media-picker.js's
  focus-trap/escape handling), new CSS. Register as a new `Library` named "media_reference" in
  crates/kernel/src/form/assets.rs (+ widget_library() match arm). No-JS fallback: a plain `<select>`
  of existing media (server-rendered options) sharing the field's `name`, which JS disables/hides once
  it enhances the field (progressive enhancement — the `no-js`/`js` root class toggle already set up by
  static/js/admin-shell.js on admin pages; CSS classes only, no inline style/script in the new template).
  Upload-new in the no-JS path: a parallel plain file input + hidden "create as `{type}`" select;
  handled by a small dedicated server-side step (only for cardinality-1 fields — documented limitation).
- **Routes** (new file `crates/kernel/src/routes/admin_media_library.rs`, merged into
  `routes::admin::router()` in admin.rs, which already carries the `admin_confirm::ask_first`
  middleware for the `?confirm` convention used by delete buttons):
  - `GET /admin/content/media` — library listing, grid+table view (`?view=grid|table`), filters
    (media type = content type among the registered set, name = title ILIKE, uploader = author_id),
    sort (newest/name), pager, bulk delete. Permission: `access media overview`. Uses the
    `ListQuery`/`ListView`/`PER_PAGE` pattern from `routes/admin_list.rs`, NOT Gather (admin listings
    never use Gather in this codebase — confirmed via admin_content.rs/admin.rs precedent).
  - `GET /media` — same handler/view as the library (this is the BL-115 fix: the plugin's
    `MenuDefinition` for `/media` was `handler_type = "page"`, which is never served by anything,
    confirmed by grepping for "page" handler dispatch — there is none, only "api" is ever routed.
    So BL-115 is fixed by registering a literal concrete route at `/media`, not by changing the
    menu mechanism). Verification requires GET /media = 200 for an editor, 403 for anonymous — do
    this via the real permission check, not an HTTP redirect, so status codes are exact.
  - `GET/POST /admin/content/media/add` (type chooser) and `/admin/content/media/add/{media_type}`
    (actual add form, permission `create media`, content_type looked up via
    `state.content_types().get(&media_type)`, validated against `state.media_sources()`).
  - `GET/POST /admin/content/media/{id}/edit` — loads item, verifies item_type is a registered
    media source (else 404), gates via `state.items().check_access(&item, "edit", &user_ctx)`
    directly (NOT the generic admin pre-gate), reuses item_form::process + `state.items().update(...)`.
  - `POST /admin/content/media/{id}/delete` — `check_access(item, "delete", ...)`, then
    `SELECT COUNT(*) FROM item_reference WHERE referenced_item_id=$1`; refuses (409 or back to list
    with a flash message) unless usage is 0 or `?force=1` was given; goes through the existing
    `?confirm` middleware like every other admin delete button.
  - `POST /admin/content/media/bulk` — bulk delete, same usage-refusal rule per row, modeled on
    admin_content.rs's `BulkActionForm::parse` (hand-parsed urlencoded body for repeated `ids[]`).
  - `GET /admin/content/media/picker` — JSON API for the dialog (list/filter/search), permission
    `access media overview`.
  - `POST /admin/content/media/picker/upload` — multipart upload-and-create-in-one for the dialog's
    "upload new" tab, permission `create media`. Use `state.files().upload(...)` then
    `state.items().create(...)` with the uploaded file id in `field_file`.
- Templates: `templates/admin/media-library-list.html` (grid+table, modeled on
  templates/admin/content-list.html + templates/admin/media-library.html, using
  templates/admin/macros/list.html macros), `templates/admin/media-form.html` (modeled on
  templates/admin/content-form.html but with the media-specific chrome/breadcrumb).
- Migration: new kernel migration `crates/kernel/migrations/20261211000001_create_item_reference.sql`
  (table + 2 indexes, additive, no backfill needed since no live usage of RecordReference-to-media
  exists yet — but DO backfill generically from every item's current RecordReference field values,
  parallel to how file_reference's migration backfills, for correctness on an existing site).
