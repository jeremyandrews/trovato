### Key design decisions (for successor context)
- JSON login (`POST /user/login/json`) takes an optional `code` field inline; a missing code for a TOTP-enrolled account gets 401 "second_factor_required" immediately (no session state). The HTML form path always redirects to `/user/login/verify` with a `PendingSecondFactor` session marker (5 min TTL, session id cycled when stored).
- Recovery completion (`/user/recover/reset`) for a TOTP-enrolled account returns `{"success":true,"next":"second_factor"}` and starts the same pending marker instead of calling setup_session.
- `setup_session(state, session, user_id, remember_me)` (now takes state) decides SESSION_ENROLLMENT_REQUIRED generically for every path (password/passkey/recovery) by calling `services::second_factor::needs_enrolment`.
- Password-login-only check `password_login_blocked_by_passkey_only` happens in attempt_login BEFORE the TOTP branch (passkey satisfies requirement; blocks a plain password login in that case with "This account signs in with its passkey.").
- Password age flag (SESSION_PASSWORD_CHANGE_REQUIRED) is set only on password logins (both branches of attempt_login and the verify-step success), via `apply_password_age_flag` (pub(crate) in auth.rs).
- middleware/second_factor.rs exempts different path sets per flag: enrollment exempts /user/two-factor, /user/webauthn, /user/passkeys (+ /user/logout, /static globally); password-change exempts /user/profile, /user/password. Token/bearer-authenticated requests are fully exempt.
- totp-rs 6.0.0 API used (Builder pattern, Secret::generate()/to_base32()/try_from_base32, Totp::check returns Option<u64> step counter used directly for replay protection via UserTotp::accept_step's WHERE last_used_step < $2). qrcodegen used directly (not totp-rs's `qr` feature, to avoid pulling qrcodegen-image → image crate conflict).
- Recovery codes: 10x 10-char base32, HMAC-SHA256 (secret_box.hmac) stored, normalized (strip hyphen/whitespace, uppercase) before hashing; displayed grouped as XXXXX-XXXXX.
