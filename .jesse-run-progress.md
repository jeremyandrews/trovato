## Research findings (do not redo this)

- `crates/kernel/src/file/storage.rs`: `FileStorage` trait + `LocalFileStorage`
  only. Header comment explains S3 was dropped pre-1.0 (legacy AWS SDK rustls
  0.21/webpki chain). BL-109 in docs/BACKLOG.md records this as a closed decision
  to be reversed by this PR.
- Workspace is already on rustls 0.23 + ring (confirmed in Cargo.lock). Kernel
  already depends on `reqwest` (0.12, rustls via workspace default), `hmac`,
  `sha2`, `hex`, `urlencoding`, `base64` — everything needed for a hand-rolled
  SigV4 signer with ZERO new dependencies.
- Rejected `object_store` crate: its "aws" feature forces `aws-lc-rs` (a second
  crypto backend alongside the workspace's `ring`) and pins its own `reqwest
  0.13` instance (can't unify with the workspace's 0.12). A minimal SigV4
  signer over the existing reqwest client avoids both problems and is small
  enough to audit. This is the PR's dependency justification.
- `file_managed.uri` already documented since its creation migration as
  `local://path` **or** `s3://bucket/key` — S3 URIs were anticipated.
- File references are found by literally scanning stored JSON/HTML strings for
  the markers `"local://"` and `"/files/"` (`crates/kernel/src/content/file_refs.rs`
  `scan_string`). Must add `"s3://"` as a third marker there.
- Existing access control: `ItemService::file_access`/`can_serve_file`
  (`crates/kernel/src/content/item_service.rs:2106-2136`) implements an
  "any-referencing" policy (D-29): viewer may fetch a file if any item
  referencing it passes `check_access(view)`, or (unreferenced) if they
  uploaded it. This already gates `/files/{*path}` and the image-style route.
  Private files add a DISTINCT, stricter concept: bytes that are never even
  reachable at a static/guessable path, served only through a dedicated
  by-id route, with storage that (for S3) has no public bucket policy at all.
- No `/file/<uuid>/download` route exists yet on main (checked: grep for "A15"
  finds nothing; `referenced_files_test.rs` comment confirms the route doesn't
  exist). This PR adds it.
- No docker, no minio binary, no network path to dl.min.io (410 Gone) in this
  sandbox. Backend tests run against a small in-process S3-compatible mock
  server built with axum (already a workspace dep), not a real MinIO. This is
  the "in process S3 compatible test server" the prompt allows as an alternative
  to MinIO.
- Field settings are a free-form `serde_json::Value` already (see
  `FieldDefinition::visible_when` in `crates/plugin-sdk/src/types.rs`). Private
  is `settings.private == true` on a File field, same convention.

## Design decided

- `FileStorage` trait gains: `size`, `describe` (status page text), `probe`
  (generic write/read/delete roundtrip, default-implemented in terms of the
  other trait methods so it works for every backend), `presigned_get_url`
  (`Ok(None)` default = backend doesn't support it), `read_stream` (defaults to
  one-shot from `read`; S3 overrides with a real streamed body).
- New `S3Storage` in `crates/kernel/src/file/s3.rs` implementing `FileStorage`
  via a hand-rolled SigV4 signer in `crates/kernel/src/file/sigv4.rs`, using the
  kernel's existing `reqwest::Client`. Settings: endpoint, region, bucket, key
  prefix, path-style on/off — all from env vars only (`S3_*`), never the
  database. `public_base_url` setting for CDN-fronted public buckets.
- Two logical "schemes": public/private, each independently mapped in config to
  a backend (local or s3). `FileService` holds `public: Arc<dyn FileStorage>`
  and `private: Arc<dyn FileStorage>` rather than one `storage`.
  `file_managed` gets a new `visibility SMALLINT NOT NULL DEFAULT 0` column
  (0=public,1=private). `StoreFile` gains a `visibility` field.
  `new_storage_uri` already dispatched on `self.storage.scheme()` — extended
  with an `"s3"` arm (URIs keep the literal `local://`/`s3://` prefix; that
  prefix names the PHYSICAL backend, not public/private-ness, which lives in
  the new DB column only).
- Private is chosen per File field via `settings.private == true`. Upload
  route gained an opt-in `visibility=private` form field so a private field's
  widget can upload straight to the private backend (no relocation needed).
  `sync_item_file_references` (file_refs.rs) ALSO flips `file_managed.visibility`
  to private, as a fail-closed defense in depth, whenever a file is attached
  to a private field — documented limitation: this flips serving policy
  immediately but does not physically relocate bytes already sitting in the
  public backend; the migrate command is the documented remediation.
- New route `GET /file/{id}/download`: looks up the file, runs the existing
  `can_serve_file` check, then serves from `self.storage_for(file.visibility)`:
  stream bytes (default) or 302 to a presigned URL if the backend supports
  presigning and `PRIVATE_FILE_SERVE=redirect` is set. This is also the
  `/file/<uuid>/download` route Ritrovo A15 wanted and the kernel didn't have.
  `/files/{*path}` and the image-style route explicitly refuse (404) when a
  resolved file's `visibility` is private — they are for public files only.
- `trovato files migrate --from <local|s3> --to <local|s3>`: moves every
  `file_managed` row currently stored in `--from`'s backend to `--to`'s
  backend, verifying size + sha256 after each copy, rewriting `uri` only
  after the copy is verified, deleting the source object only after the DB
  row commits. Resumable for free: an interrupted run leaves some rows
  already rewritten to the target scheme and others not; a rerun only
  processes rows still on the source scheme, so it picks up exactly where it
  left off with no separate journal.
- Status report (`admin_reports.rs::files_requirement`) now reports both
  schemes using `FileStorage::describe()` + `FileStorage::probe()`.

## Known, accepted limitations (document in the PR, do not silently drop)

- `sync_item_file_references` flips `visibility` to Private immediately but
  does NOT relocate bytes already written to the public backend — the
  migrate command is the documented remedy. A field known to be private
  BEFORE upload should use `FileService::upload_private`/`StoreFile{
  visibility: Private }` instead, which writes directly to the private
  backend with no relocation ever needed. This is called out in the struct's
  doc comment in `file_refs.rs`.
- Rich text / page-builder content referencing a file only via its
  `/files/{path}` URL (not a raw `local://`/`s3://` string) cannot be told
  apart from local vs S3 by the reference scanner (`file_refs.rs::
  scan_string`) — it always normalizes to `local://{path}`. Pre-existing
  scanner limitation, now slightly wider scope (previously everything WAS
  local). Documented in that file's module doc.
- Image style derivatives are still cached on local disk
  (`ImageStyleService::cache_path`), even when the original is S3-backed.
  Not a security issue (the route still gates on the original's access
  check and now also its visibility), just not multi-pod-safe for the
  derivative cache specifically — pre-existing limitation (the whole
  feature this PR fixes is "local disk doesn't work multi-pod"; the
  *original* now can live on S3, the generated thumbnail cache doesn't yet).
  Worth a BACKLOG entry if there isn't time to fix it in this PR.
