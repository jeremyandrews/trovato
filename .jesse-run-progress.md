- Deep research done (via Explore agent + manual reads). Key findings:
  - `content::submission::build_item_fields` only ever writes content-type-DECLARED
    fields. A `tap_form_alter`-added input whose name isn't declared in the type's
    schema never reaches `item.fields` via the HTML form path.
  - `tap_form_submit` (fires AFTER save, args `{form_id, values, item_id}`) gets
    `values` filtered to `rendered_fields` (NOT schema) — so a plugin-added input's
    raw posted value DOES reach it. Design: write field_publish_on/unpublish_on via
    a single-key raw SQL merge (`fields || jsonb_build_object(...)`) from
    `tap_form_submit`, exactly like the plugin's own RESTORE_PUBLISH/UNPUBLISH
    pattern. Then call the plugin's own `sync_timers()` directly (not via a tap)
    after re-fetching the item, since `tap_item_insert`/`tap_item_update` already
    fired earlier in the save (before our raw SQL write existed) and won't fire again.
  - `gate_field_writes` (item_service.rs) starts `out` from a clone of *submitted*
    fields: an editable field omitted from a submission is silently dropped, not
    copied from stored. So NEVER call `host::save_item` with a partial fields
    object (would wipe unrelated fields) — use raw SQL for the single-key merge.
  - For the JSON item API: `check_json_fields` only validates declared fields;
    undeclared keys (field_publish_on/unpublish_on) pass through as-is and DO get
    persisted normally (gate_field_writes keeps them, since no plugin declares an
    access decision for them => fail-open editable). So JSON storage already works
    with zero kernel changes; only VALIDATION is missing for that path.
  - Kernel seam (minimal, justified, to be added + tested):
    1. `tap_form_validate`'s dispatched input in `FormService::process` gains
       `item_id` (currently only `{form_id, values}`) — symmetric with
       `tap_form_submit` which already includes it. Needed so a plugin can look up
       the item's CURRENT stored status/fields to apply "already published" and
       "unchanged" exemption rules.
    2. New `FormService::validate_fields()` method, dispatching the SAME
       `tap_form_validate` tap for the JSON item API path (routes/item.rs
       `submitted_fields`'s JSON branch), with `form_id: "json_item_{type}"` so the
       plugin's one `tap_form_validate` function serves both the form and the JSON
       API ("one validation function used by the form and by the JSON item API").
  - Timezone: no site-wide default exists in the codebase (grepped). Decision:
    user.timezone, else UTC. No chrono-tz; follow `admin_timers.rs`'s existing
    Postgres `AT TIME ZONE` pattern (`viewer_zone`/`local_times`/`parse_local`),
    called from the plugin via `host::query_raw`.
  - DST gap/overlap: tested empirically against the real Postgres in this pod.
    Algorithm (verified working): compute candidate UTC instants using the zone
    offset 2h before and 2h after the wall-clock time (both outside any transition
    window), round-trip each back through `AT TIME ZONE` to see if it reproduces
    the typed wall-clock: neither matching = gap (refuse), both matching = overlap
    (take min = earlier instant), proceeding normally otherwise.
  - `/admin/content/scheduled` (the plugin's existing gather-query listing) is
    pre-existing NOT ROUTED (404) per docs/BACKLOG.md BL-115 — a separate, already
    tracked, open bug, out of this task's scope. Will note in PR body rather than
    fix (fixing the gather/menu-routing system is a large separate effort).
  - trovato_book's module doc claims tap_form_alter/validate/submit "are never
    dispatched" for the item form — STALE relative to current main (item_form.rs
    clearly calls FormService::build/process now). Not touching it (out of scope).

## Log (continued 2)
- Wrote `crates/kernel/tests/scheduled_publishing_form_test.rs`, 12 integration
  tests against the real router + real WASM plugin (timer_plugin_test.rs /
  form_pipeline_test.rs style static-app harness). Hit two real bugs during
  debugging (found via a long trial-and-error session — eprintln! from WASM
  traps the whole module in this runtime, a dead end that cost real time;
  the actual fix was unrelated):
  1. **`host::get_item` answers a denied VIEW the same as a missing item.**
     An editor holds `edit` on their own unpublished draft but typically NOT
     a separate `view own unpublished content` permission. Every read in
     `tap_form_alter`/`tap_form_validate`/`tap_form_submit` was using
     `host::get_item`, so for a perfectly normal unpublished item being
     edited by its own author (no special permission), the plugin saw "no
     such item": the edit form failed to prefill an existing schedule, the
     "already published" check defaulted wrongly, and the write in
     `tap_form_submit` silently did nothing. Fixed by adding `read_item()`,
     a `host::query_raw` read of `item.fields`/`status` straight off the
     `item` table (not a protected table), bypassing that view gate — safe
     because every caller only runs for an item the kernel's own route
     already decided this request may edit. This was the one genuinely
     important correctness bug found this session; call it out prominently
     to critics and in the PR body.
  2. `current_user_id`/`current_user_has_permission` need `user-api` in
     `host_interfaces` (gated by `crates/kernel/src/host/mod.rs`'s
     `HOST_INTERFACE_REGISTRARS`), and `load_users` additionally needs
     `user_directory = true`. `users` is a protected table
     (`crates/kernel/src/plugin/db_policy.rs` `PROTECTED_TABLES`), so
     `host::load_users` (not raw SQL) is the only way to read a user's
     timezone from a plugin. Both added to the plugin's info.toml.
  Final write design: `tap_form_submit` reads via `read_item`, merges the
  two resolved keys into a full `fields` clone, and writes via
  `host::save_item` (never a partial object — would wipe unrelated fields;
  never raw SQL for the write itself — `ItemService::load`'s cache would go
  stale and `tap_item_update`/`sync_timers` would not fire automatically).
